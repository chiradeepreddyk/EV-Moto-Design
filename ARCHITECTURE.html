01 The idea that explains every decision

Open index.html in a browser and the whole thing runs. No build, no npm, no server, no network request. All physics is hand-written JavaScript; all state lives in memory and localStorage.

A finite number is not an accepted design.

The codebase treats mathematical validity and engineering acceptance as two independent axes, and never lets the first imply the second.

Every result object carries both axes, so the interface can say “this equation solved cleanly” and “nobody has approved this” in the same breath:

AxisFieldValues
Did the maths run?runtimecurrent · stale · failed
Is it engineering-approved?assessmentnot_evaluated · conflict_invalid

Nothing in the application can promote a value to “approved” — that requires physical validation outside the tool. It is why the release gates read not evaluated in perpetuity, why the benchmark table states outright that proximity to a Yamaha creates no pass, and why almost every panel carries a scope disclaimer.

Why the orphans are orphans

They target DOM ids — elecSeriesCells, elecPackMass — that no longer exist in the current HTML. Leftovers from an earlier version. Deleting all three changes nothing.

The stranded dataset

The live benchmark feature reads the five-record powertrain-benchmarks.js. The 2,037-record scrape is never consulted.

The missing contract

The governing PRD is not in version control. prd-data.js and verify-core.js are the only surviving encoding of it.

03 Layering

Script order in index.html is also the dependency order. Each layer may read downward and never upward — and the boundary that matters most is the one under app.js.

Every file is wrapped as (function (global) { "use strict"; … })(window). No ES modules, no bundler, and no global namespace pollution beyond the three published objects.

04 One object holds the configuration

loadState() clones PRD_DATA.defaults, deep-merges whatever is in localStorage, then repairs legacy data — collapsing retired scenario names into the three supported macro states and deleting obsolete sag keys a previous version wrote.

state = {
  meta: {
    project, configuration, revision,        // increments on EVERY edit
    units, frame, loadCase,                  // Kerb | Solo rider | Rider + pillion
    dutyCase,                                // Road | Urban | Grade | Performance
    electricalScenario,                      // drive | charge | off
    architectureVariant,                     // 5 E/E topology templates
    domainRevisions: { stance, steering, … } // per-domain counters
  },
  stance,     // 55 fields — wheelbase, rake, tyres, hardpoints, anthropometry
  steering, suspension, antiSquat, sensitivity, sag,
  powertrain, vehicle, battery, electrical,
  components: [ … ]  // 15 electrical instances: mass, X/Z, power, states
}

Two storage keys, deliberately separate

KeyHoldsBumps revision?
moto-geometry-prd-v1.3The engineering configurationYes
moto-geometry-ui-v1.3Diagram node positions, view layer, open panelsNo

The split is enforced on purpose. Dragging a node in the electrical network is a presentation change and must never create a design revision — a rule the code repeats in three separate places.

05 The solver chain

EngineeringCore.calculate(state) runs the entire model in a fixed order. Each function returns {ok: true, …} or invalid("message") — there is no exception-based control flow, and no partial result is ever presented as current.

What each solver actually does

FunctionMethod
tyreNominal diameter from width/aspect/rim — the single source of every wheel radius in the app
ergonomicsTwo-link inverse kinematics. Circle intersection finds the elbow from shoulder + grip and the knee from hip + peg, then reports joint angles and clearances
steeringFoale trail, wheel flop, kinematic turn radius, quasi-static braking transfer, rigid-body wheelie and stoppie limits from the live CG
rearKinematicsAtRotates the swingarm about the pivot to a target axle height, then solves the rocker/dogbone linkage by circle intersection. Handles direct and linkage architectures
suspensionSweeps that solve across travel, differentiates shock against wheel displacement for local motion ratio, derives wheel rates and the fork air spring
componentMassPropertiesMass-weighted CG over glider, rider, pillion, luggage and all 15 electrical components; static beam solve for axle loads. Rejects a CG outside the wheelbase
sag64-iteration bisection finds where dual-rate spring force equals sprung load. Rear shock stroke is interpolated from the linkage curve, never aliased to wheel travel
antiSquatUpper chain tangent between sprocket pitch circles, intersected with the swingarm line, gives the force centre and Foale percentage — cross-checked against the Cossalter reciprocal
gearingOverall ratios, per-gear curves at 41 points each, sprocket pitch radii, ideal chain link count, named duty point
electricalPack S/P model, quadratic constant-Voc discharge solve, breadth-first LV reachability, DC-DC headroom, cable drop, precharge RC
batteryStudyRequired energy to a proposed S/P pack, AC supply limits, charge time with taper, two runtime models
sensitivityClones the state, perturbs one parameter ± step, and calls calculate() recursively on each clone

The recursion guard

function sensitivity(state, calculate) {
  const plus  = JSON.parse(JSON.stringify(state));
  const minus = JSON.parse(JSON.stringify(state));
  plus [path[0]][path[1]] += step;
  minus[path[0]][path[1]] -= step;

  const baseResults  = calculate(base,  false);  // ← false disables sensitivity,
  const plusResults  = calculate(plus,  false);  //   preventing infinite recursion
  const minusResults = calculate(minus, false);
}

Because the whole model is re-solved, the derivatives are real rather than analytic approximations. The routine then classifies each output as linear, mildly nonlinear or nonlinear by comparing forward against backward differences.

The subtlest piece: LV reachability

A low-voltage component is not counted simply because it is selected and enabled. The code walks outward from the DC-DC and LV battery, following only enabled LV power edges, and counts a load only if it is genuinely reachable:

const reachable = new Set(/* dcdc and lvBattery nodes */);
let changed = true;
while (changed) {
  changed = false;
  graph.edges.filter(/* enabled LV edges between active nodes */).forEach(edge => {
    if (reachable.has(edge.fromNodeId) && !reachable.has(edge.toNodeId)) {
      reachable.add(edge.toNodeId); changed = true;
    }
  });
}

An orphaned load raises “Active LV component X has no enabled source path” rather than silently inflating the power budget.

06 What a keystroke actually does

There is no virtual DOM and no reactive framework. Every single input event rebuilds the entire application.

Rendering style

Every renderer is a function returning a template literal. There is no component model:

function renderSteering(tab) {
  const o = outputs.steering;
  return `<section class="view ${activeTab === tab.id ? "active" : ""}">
    ${viewHead(tab)}
    ${input("steering.upperOffset", "Upper offset", "mm")}
    ${metric("Ground trail", o.groundTrail, { owner: "steering" })}
  </section>`;
}

Three helpers carry most of the weight:

  • input(path, label, unit) — emits a field wired by data-path, so the handler knows exactly which state key to write.
  • metric(name, item) — emits a result card with both badges, resolving failed when the parent solver returned ok: false and stale from the stale set.
  • linkedField(path) — a read-only mirror of another tab's value, labelled with its owner and source revision. Single ownership, made visible.

Everything interpolated passes through esc(), which matters because project names and component labels are free text.

07 Staleness propagation

Editing a field does not just invalidate its own tab. A dependencies map declares who consumes whom, and every consumer picks up a stale badge and a nav dot.

stancesteering, suspension, sag, powertrain, electrical, sensitivity, vehicle, battery, anti_squat
steeringsuspension, sag, sensitivity
suspensionsag, anti_squat, sensitivity
saganti_squat, sensitivity, electrical
powertrainvehicle, anti_squat, electrical, battery
electricalstance, sag, anti_squat, vehicle, battery, sensitivity

Note the last row: electrical → stance. Component mass feeds back into the vehicle CG, so changing a battery mass correctly marks the packaging tab stale. The graph is a cycle, not a tree, and the code models it as one.

08 The drawing engine

Five SVG constructions are generated from solver output — they are drawings, not illustrations. All of them share one auto-fitting transform that takes the extreme points of the construction, adds a four percent margin, and computes a uniform scale so X and Z are never distorted:

const scale = Math.min((width - 2*pad)/(xmax - xmin),
                       (height - 2*pad)/(zmax - zmin));
return { scale, tx: x => x0 + x*scale,
                ty: z => z0 - z*scale };   // Z flips: +Z is up
DiagramDraws
steeringDiagramSteering axis, fork axis, ground trail, the normal-trail perpendicular, both tyres to scale
suspensionDiagramRear swingarm at extension, mid and bump; rocker and dogbone; fork travel
antiSquatDiagramSprocket pitch circles, chain tangent, force centre, loaded CG, the 100% reference line
sagDiagramLoaded chassis against the unladen reference, with pitch applied along the wheelbase
powertrainDiagramFunctional torque path, plus a true-scale sprocket and chain construction

The interactive network

The Energy & E/E view renders nodes and bezier edges that are draggable by pointer and movable by arrow key for keyboard users. Positions save under architectureVariant:nodeId in the UI key — never the engineering state. Edges dim when inactive in the current scenario, and each node subtitle carries live flow: 38.4 kW out, 312 W LV.

Canvas charts

drawCharts() plots only the active tab — motion ratio against travel, anti-squat against travel, per-gear speed against RPM, and a loaded-versus-unladen geometry comparison. It scales for devicePixelRatio and redraws on resize.

09 Verification

verify-core.js runs under Node with a one-line shim — possible only because the core is DOM-free. It is strict in two distinct ways.

Numeric fixtures pin exact values

near(trail.groundTrail.value, 115.470053838, 1e-6, "Foale ground-trail fixture");
near(defaultOutputs.antiSquat.reciprocalCheck.value, 1, 1e-9, "reciprocal identity");

Source-text assertions freeze past mistakes

check(!/three\.js|gltf|parametric 3d/i.test(text), "excluded 3D scope");
check(!appSource.includes('metric("Fork air pressure"'), "card must stay removed");
check(!/front wheel sag|rear wheel sag/i.test(appSource),
      "Sag UI must not present wheel displacement as sag");

That last assertion is the interesting one. An earlier version reported rear wheel movement and called it sag. Real sag is shock stroke, which differs by the motion ratio. The correction is now defended three separate ways — a numeric check proving the two values differ, an interpolation check proving the linkage curve is used, and a text check preventing the old wording from ever reappearing.

Not confirmed: node is not installed on this machine, so the suite could not be executed to verify it currently passes.

Conventions worth preserving

  1. The core stays DOM-free. It is the single property that makes the model testable in Node.
  2. Return invalid(message), never throw. The interface renders the message verbatim to the engineer.
  3. Every result goes through result(value, unit, definition) so it carries a unit, a plain-English definition and both status badges.
  4. Escape everything with esc() when interpolating into HTML.
  5. Presentation state never touches the engineering revision.
